## Current architecture and flow

1. App/window notifications, polling and the periodic timer request a settled screenshot. Existing foreground sensitive-context filters apply. Capture metadata includes window geometry, browser context, input recency and sampled pointer position.
2. With explicit `--input-events --input-app com.microsoft.VSCode`, native input passes permission, global secure-input, focused role/subrole/owner, context-boundary, target-process and timing checks. Unknown/protected context produces a gap.
3. `input_events.py` reduces permitted input into keyboard counts, coarse movement/drag/click and scroll summaries. Ctrl+Tab/Cmd+Tab and Shift variants are classified transiently; raw keycodes/modifiers and characters are never stored. Other keyboard activity remains counts.
4. `input_store.py` persists summaries and links them to before/after captures. Before-image age is explicit. Keyboard/scroll burst completion, clicks and shortcuts can request debounced captures; movement alone does not.
5. Background Apple Vision OCR feeds `understand.py` and `activity.py` heuristics plus `memory_content.py` excerpts. OCR runs outside the shared memory lock.
6. Item identity resolves durable memory; sessions record visits. Exact-frame notes attach after OCR or remain unresolved. Input links gain resolved item IDs.
7. CLI exposes items/content/events and controls. Contribution records support safe reconstruction/deletion. There is no semantic recall service or shared agent API yet.

Storage: `.index.json` is the full internal item state; `memory.json` is its readable `things` export. Sessions, inputs, input source images and contribution evidence live under `data/memory/`. Details and file responsibilities are in the handover.

## Next build — foreground evidence design in review

**Foreground-window evidence quality is the next development increment.** The goal is to retain the actual work area consistently and keep surrounding UI from becoming memory evidence. Input is useful only if the screenshot/OCR it links to represents the correct work.

Proposed first slice:

1. Select the actual foreground/focused window; address Safari's toolbar-sized candidate without replacing legitimate focused dialogs with an arbitrary largest window.
2. Establish one validated window/display geometry and coordinate mapping across capture, content extraction and activity comparison, including multiple displays and changed bounds.
3. Use that mapping to isolate permitted source pixels before saving/processing. Treat cropping as a data/coordinate change requiring explicit design and migration-compatible metadata, not just a post-OCR filter.
4. Validate browser body text, editor content, dialogs and display placement with controlled fixtures and a short live sequence. Unknown/changed geometry should be visible rather than silently interpreted as a full valid document.

The user selected this next build and approved the [written design](docs/superpowers/specs/2026-10-05-foreground-evidence-design.md). The [implementation plan](docs/superpowers/plans/2026-10-05-foreground-evidence.md) is written and self-reviewed; product implementation has not started. The design chooses direct, verified window capture, versioned source geometry, conservative skip behavior, historical-frame compatibility, and fresh OCR across geometry boundaries. Initial support covers windows fully contained on one display; spanning/off-screen windows remain explicit skips. Written-plan review is pending under the Superpowers architectural workflow; preserve native execution in this session followed by one independent review.

## Limits to preserve

- Only VS Code input is allowlisted. The input allowlist does **not** scope ordinary screenshots: they still cover full displays and include sampled pointer positions. Foreground filters/rectangular OCR bounds do not eliminate overlapping/background sensitive content.
- JSON/JPEG remains plaintext. New input/control/provenance files have private permissions, not encryption. There is no external model/backend; a future hosted agent might send retrieved context off-device unless separately controlled.
- Detailed input/source copies: 30s transient bound, up to 24h disk retention configurable shorter, 4,096-event cap. Startup/periodic/inactive inspection pruning enforces expiry; a stopped process has no wall-clock deletion scheduler. Ordinary memories/notes/excerpts/contributions retain longer-lived evidence.
- Ctrl+Tab/Cmd+Tab counts are accepted observed steps, not a reliable count of windows passed. Cmd+Tab navigates apps; Dock/switcher focus can cause deliberate omissions. Exact selection/ranking is not modeled.
- Global secure input, missing focus/target metadata, unverified text fields and events delayed beyond 100ms continue to fail closed. Do not relax these guards merely to remove visible gaps.
- Activity/decision-phrase rules are heuristic. Decision quotes are unverified observed words; screenshots cannot establish intent, author, task completion or reason by themselves.
- Stable Google Docs identity does not solve every app or merge old duplicates. Changed small regions can reuse stale OCR; overall time remains approximate.
- Legacy provenance, active trackers, replay references, external changes and shared screenshots can block deletion. Do not invent ownership/replacement evidence to make it succeed.

## Commands

```bash
.venv/bin/python lmemm.py --input-events --input-app com.microsoft.VSCode
# Run controls/inspection from another terminal:
.venv/bin/python lmemm.py status
.venv/bin/python lmemm.py pause
.venv/bin/python lmemm.py resume
.venv/bin/python lmemm.py memory 100 --events --content
# After stopping, preview deletion of a disposable test session:
.venv/bin/python lmemm.py delete-session SESSION --dry-run
.venv/bin/python -m unittest discover -s tests -v
```

Run one tracker, grant permissions to its launching app, restart after code/permission changes, and type in an editor file for the input check. README and HANDOVER.md contain setup and detailed acceptance instructions.
